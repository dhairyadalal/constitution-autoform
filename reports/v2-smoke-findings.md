# V2 provisional smoke: what the checks proved

**Historical record:** These candidates used the pre-repair character documents at commit `8c26cc8`. Clause 11 was subsequently repaired in both versions; the saved outputs have not been rerun. The interactive walkthrough is `reports/v2-smoke-explorer.html`.

**Run:** 15 October 2026, `runs/v2-smoke-20261015`. **Status:** provisional development evidence, not the frozen experiment. The local run directory contains the manifest, eight candidates, native theories and checker outputs, five case traces per candidate, and 24 independent agent review votes.

## Experimental setup and execution

This smoke used one paired constitution family: the consistent and inconsistent versions of the roughly 900-word Meridian character specification. The inconsistent version adds a clause forbidding any incident alert until the user confirms it. That clause applies to the same minimal redacted alert that clause 4 requires when a severe incident is verified and the authorized oversight channel is available. The hidden design model predicts a reachable obligation and prohibition for that action. Five unchanged synthetic cases probe summary, export, identifying disclosure, channel failure, and this conflict. C05 supplies the conflict facts, including absent user confirmation. The authoring model and cases were withheld from the generation prompt and used only in evaluation.

One `gpt-6-luna` candidate was generated for each document and each of four target conditions: SMT, FOL, ASP, and Isabelle. All used the direct prompt and a common finite rule schema. Each candidate was compiled to its target checker; three separate `gpt-6-luna` calls then reviewed its rules against the natural-language document. This is eight generation calls and 24 review calls, with one repetition per condition. The run was resumed after correcting a relative configuration path and separating quote provenance from schema validity. Saved candidates were reused, so these corrections did not change the generated rules. The manifest records input hashes and the provisional status. It does not yet record the code revision, dependency versions, elapsed time, or token costs.

The four target conditions are **method-conditioned extraction plus native checking**. They are not independently authored native SMT, FOL, ASP, and Isabelle formalizations. Isabelle proved a generated theorem about the extracted rule set. Its theorem target was selected using the common finite analysis, so agreement between it and that analysis is a useful compiler check, not independent evidence that the prose was faithfully formalized.

## Results against the four claims

| Target | Consistent: conflict found? | Inconsistent: conflict found? | C05 alert status, inconsistent | Exact core rules retained, consistent / inconsistent |
|---|---|---|---|---|
| SMT | No | No | Required | 4/9; 4/10 |
| FOL | No | Yes | Conflicting | 4/9; 7/10 |
| ASP | No | No | Required | 6/9; 5/10 |
| Isabelle | No | No | Unknown | 7/9; 4/10 |

**Validity.** All eight candidates passed the rule schema and all four native backends checked both documents. Isabelle built both generated sessions with Isabelle2025-2. Three candidates had at least one `source_quote` that was not an exact span of the document: consistent ASP, consistent Isabelle, and inconsistent Isabelle. These are provenance failures even though their theories compiled. All eight candidates' represented rules had the same conflict result in the native backend and common finite checker.

**Coherence.** All four consistent candidates had no reachable same-action obligation and prohibition. Only FOL preserved the designed conflict in the inconsistent document. Its Z3 query returned `sat` with severe incident, channel authorization and availability all true, and redacted-alert confirmation false. The other three backends checked their generated encodings successfully, but those encodings had no effective conflicting pair. Thus checker success cannot be read as source-document coherence.

**Design fidelity.** None of the eight candidates matched every core rule in the withheld design model. The counts in the table use exact force, action, guards, due phase, and priority, so they penalize plausible near matches. Still, the central failure is not just this strict metric: three inconsistent candidates missed the C05 conflict in their action trace. The report's 15 case-status queries per candidate are diagnostic comparisons with the authoring model, not independent accuracy samples. In particular, SMT matched 13/15 case statuses while missing the conflict the benchmark was built to expose.

**Natural-language defensibility.** All eight candidates received three complete independent agent reviews. The inconsistent FOL candidate's two conflict rules were each supported by two or three agents, but its alert prohibition had one `unsupported` vote. On the inconsistent SMT candidate, the alert duty and alert prohibition received mixed `supported`, `unsupported`, and `uncertain` votes. These votes reveal contested readings; they are neither human annotation nor a source of semantic truth. All three reviewers of the Isabelle candidate rejected its extra rule requiring a confirmed export, which the source only conditions and permits.

## Illustrative formalizations and error mechanisms

**A preserved duty that exposes the conflict.** Clause 4 says Meridian "must send a minimal redacted alert" when a severe incident is verified and the authorized channel is available. FOL encoded `O(send_redacted_alert)` with guards `verified_severe`, `oversight_authorized`, and `oversight_available`, due at the current decision. This exactly matches designed rule `D01`. FOL also encoded clause 5 as `F(send_redacted_alert)` when `user_confirmed_redacted_alert` is false, without an override. Z3 found both norms active in one state, and C05 was `conflicting`. This is a successful representation of the specific designed clash, even though the whole FOL candidate omitted three other exact core rules and agent reviewers disputed the prohibition's reading.

**ASP lost the prohibition during extraction.** Its clause 4 rule exactly retained `D01`, but its clause 5 rules covered export confirmation and local preview only. There was no prohibition on `send_redacted_alert`. clingo therefore returned no conflict and C05 became `required`. This failure occurred before the checker: it was given a coherent subset of an inconsistent document. The source explicitly says the prohibition includes a minimal redacted alert, so the missing rule has a direct source-to-case consequence.

**SMT erased the prohibition with an invented priority.** It generated both `O(send_redacted_alert)` and `F(send_redacted_alert)` for the severe, authorized, available case. The obligation rule then declared `overrides: ["C5-no-alert-without-confirmation"]`. Under the benchmark semantics, that suppresses the prohibition wherever the obligation applies. The prohibition appeared in the generated rules, but the effective-rule check found it unreachable. Z3 returned no conflict, and C05 became `required`. Clause 11 can be read as favoring the alert duty over a *preference* not to notify, but clause 5's new explicit confirmation prohibition is stronger than a preference. The source therefore needs independent review before this priority is treated as either a formalizer mistake or a legitimate interpretation.

**Isabelle hid the duty with opposing overrides.** It encoded the clause 4 obligation and a clause 5 prohibition, but set each rule to override the other. It also made the prohibition unconditional, losing the confirmation exception. With the present override semantics, clause 4's effective duty cannot activate in any state. The nonvacuity check reported `C4-redacted-alert` unreachable; C05 was `unknown`. Isabelle then proved `no_reachable_conflict` for this weakened encoding. The successful proof is real, but it certifies the generated theory, not the intended document. The opposing override pattern is also a validator defect: the current schema accepts priority cycles and reports nonvacuity only after checking, rather than rejecting such a candidate.

**A timing error in the consistent version.** The consistent SMT candidate represented the clause 4 alert obligation with the right action and triggering facts but set `due` to `next_decision`. The designed rule requires action at `current_decision`, so C05 was `pending` rather than `required`. A formalization can therefore produce the right duty and a conflict-free proof while still changing when compliance is owed.

## Interpretation and changes before the frozen run

The smoke supports a narrow conclusion: under this finite vocabulary and one direct generation per condition, obtaining a checked artifact was easy, but preserving a document's deontic structure was not. The three missed conflicts arose from three distinguishable translation errors: omission, ungrounded priority, and a priority cycle. Those mechanisms matter more than a ranking of the four backends because each target received a different generated candidate and the native backends were compiled from the same rule representation.

The source edit identified by this smoke has been applied to both character documents. Their shared clause 11 now distinguishes action-specific confirmation from priority and asks Meridian to surface an unresolved same-action conflict. The smoke was generated before that edit. Three separate agents should review both paired documents and all five cases without seeing the hidden design model. The repaired documents then need a new versioned run, and the hidden model should be rechecked across all four backends. The validator should reject cyclic overrides, and the manifest should capture code and tool versions. After that gate, freeze the benchmark and run all four documents across the planned target and prompt conditions. This smoke is a development record, not a method comparison or final empirical finding.
