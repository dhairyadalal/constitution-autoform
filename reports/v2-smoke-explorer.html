03 / Error analysis

Three encoding errors removed the conflict

Under the authoring model, C05 activates clause 4’s duty and clause 5’s prohibition for the same redacted alert. FOL retained both. The other candidates changed the effective rule set before the backend query.

∅

ASP omitted clause 5’s alert rule

The candidate included O(send_redacted_alert) but no corresponding prohibition. clingo found no conflict in that rule set. It classified the C05 alert as required.

↗

SMT introduced priority

Both forces appeared in the candidate, but the duty overrode the prohibition wherever both applied. Z3 found no effective conflict. The prohibition could not activate after the override.

↔

Isabelle candidate used opposing overrides

Each alert rule overrode the other. The duty had no effective witness; C05 was unknown. Isabelle proved no_reachable_conflict for that encoding.

FOL encoded both rules without an override. Z3 found a witness with severe incident, authorized available channel, and absent user confirmation. C05 was conflicting. One of three agent reviewers judged the prohibition unsupported; the checker result does not settle that interpretive disagreement.

This run identifies translation errors to measure separately: omitted rules, changed guards or due phases, and unsupported priority relations. With one candidate per target condition, it does not estimate relative method performance.

04 / Benchmark revision

The paired documents now share a neutral clause 11

The smoke text said clause 5 concerned export confirmation, even after the inconsistent version added an alert-confirmation rule there. The revision removes that stale cross-reference in both documents. Clause 5 remains the only difference between the pair.

Evidence: local run runs/v2-smoke-20261015, eight candidate JSON files, native checker artifacts, case diagnostics, 24 review votes, and input hashes. Exact design matches require the same force, action, guards, due phase, and overrides. Agent votes are interpretations rather than human labels. The finite checker establishes properties of generated rules under stated assumptions; it does not establish natural-language fidelity or eventual compliance.
